# Publishing on extensions.gnome.org (EGO)

How GNOME Critter gets from this repository to
<https://extensions.gnome.org>, and what to redo for each new version.
Rules: <https://gjs.guide/extensions/review-guidelines/review-guidelines.html>.

Points marked *unverified* are what the guidelines or tools suggest but
haven't been confirmed against the live site.

## How a release goes

1. `scripts/check-release.sh` builds `dist/gnome-critter@beedi.xyz.shell-extension.zip`
   and checks it (see below). It must end with "Ready to upload".
2. Install that zip as is on a clean session and try it:
   ```
   rm ~/.local/share/gnome-shell/extensions/gnome-critter@beedi.xyz   # if it is the dev symlink
   gnome-extensions install --force dist/gnome-critter@beedi.xyz.shell-extension.zip
   ```
   Log out and back in (Wayland has no hot reload), then
   `gnome-extensions enable gnome-critter@beedi.xyz`, check `gnome-extensions info`
   (`ACTIVE`), open the preferences, play a minute, and read
   `journalctl --user -g Critter`.
3. Upload the zip at <https://extensions.gnome.org/upload/> (an account is
   needed; the terms of service must be accepted). The site assigns the version
   number; the extension becomes "pending review".
4. Reviewers answer on the extension page (and by e-mail). If refused, fix,
   rebuild, upload a new zip.
5. Once accepted, fill in the extension page (screenshots; the text comes from
   `metadata.json`).

Every new version goes through the review again, and supporting a newer GNOME
Shell means uploading a new zip with the wider `shell-version`.

## What the archive must contain

- `metadata.json` with `uuid`, `name`, `description`, `shell-version` and `url`
  (the public repository, where reviewers read the code). `version` is managed by
  the site: never set it. `version-name` is free (1 to 16 characters).
- `extension.js`, `prefs.js`, the GSettings schema XML, `LICENSE`, the code
  (`lib/`, `core/`), `packs/`, `assets/`, `locale/*.mo`.
- No `gschemas.compiled` (the installer compiles the schemas itself: checked
  on GNOME Shell 50), no `.po`/`.pot`, scripts, `__pycache__`, binaries or the
  `critter-demo` reference pack.

`uuid` (`gnome-critter@beedi.xyz`) can never change once published.

## What `scripts/check-release.sh` checks

`metadata.json` fields (real https `url`, no `version`, `version-name` length,
stable `shell-version`), the archive's contents (required and forbidden files,
size), the code (no `Mainloop`, `Lang`, `ByteArray` or `imports.`; no Shell
library in `prefs.js`; no Gtk/Gdk/Adw in the Shell's process) and `npm test`.

## Where the project stands against the review rules

| Rule | State |
|---|---|
| Public repository at `url` | `https://github.com/SoftMadHatter/gnome-critter`, a push mirror of the private GitLab (`master` only) |
| GPL-compatible license | `GPL-3.0-or-later`, `LICENSE` in the archive |
| Supported versions | `shell-version: ["50"]`: the only version tested. Add 48/49 only after a real test (`Clutter.ClickGesture`/`PanGesture` are not confirmed on 48) |
| Everything created in `enable()` destroyed in `disable()` | audited (timers, signals, actors, grabs, modal dialogs, idle sources) |
| `prefs.js` imports | Gtk, Adw, Gio, GLib and `core/` only |
| No forbidden modules, no network, no subprocess, no clipboard, no telemetry | checked by the script and by review of the code |
| No excessive logging | `console.warn` at startup only |
| Copyrighted material | sprites and sounds are generated by `scripts/gen_*.py`; no third-party asset |
| Code written with an AI assistant | allowed; reviewers reject superfluous or inconsistent code, invented APIs and comments that read as instructions to a model. The code was reviewed in full before the first upload |
| Archive size | about 2.4 MB (sprites are palette PNGs); no size limit found in the rules (*unverified*) |

## Automation (not set up)

- Building and checking: done (`scripts/build.sh`, `scripts/check-release.sh`).
- Uploading: `gnome-extensions upload --user ... --password-file - --accept-tos <zip>`
  exists in GNOME Shell 50 (`gnome-extensions help upload`); it only drops the
  zip, the review stays manual.
- A CI job on a `v*` tag could build, check and upload; each upload starts a
  review, so it should never run on every merge. The credentials would be masked
  CI variables, never on the command line. *Not done yet.*
